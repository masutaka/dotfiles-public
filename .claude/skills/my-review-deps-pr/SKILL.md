ghro CLI で $0（GitHub PR URL または PR 番号）をレビューして、`tmp/docs/pr-review-{PR番号}.md` にまとめて。

$0 が指定されていない場合は、ユーザーに GitHub PR URL または PR 番号を確認すること。

## 準備

リポジトリ特定:

- GitHub PR URL が渡された場合は URL から `owner/repo` をパースし、ghro に `--repo owner/repo` で渡す
- PR 番号だけが渡された場合は cwd の git リポジトリの origin から `owner/repo` を判定する。判定できなければユーザーに確認する

bot の判別:

PR body の書式が bot ごとに違うので、最初にどちらの PR かを判別する。メタ情報の `author` と `headRefName` を見れば分かる:

- Dependabot: author が `app/dependabot`、ブランチが `dependabot/...`
- Renovate: author が `app/renovate` など、ブランチが `renovate/...`。body 末尾に "This PR was generated by Mend Renovate" などがある

PR タイトルと更新対象の把握:

- Dependabot のタイトルは `bump <パッケージ名> from <旧バージョン> to <新バージョン>` の形式が多い
- Renovate のタイトルは `chore(deps): update <パッケージ名> action to <新バージョン>` や `update dependency <パッケージ名> to <新バージョン>` の形式が多く、旧バージョンは含まれない。body 冒頭の表（Package / Type / Update / Change）から旧→新バージョンと更新種別（major / minor / patch / digest など）を取る
- どちらの bot も、1 つの PR で複数パッケージを更新することがある。パッケージごとに調査する
  - group 設定: Dependabot は `bump the <グループ名> group ... with N updates` のようなタイトルで、body に更新一覧が並ぶ。Renovate は body 冒頭の表に複数行が並ぶ。Renovate の lock file maintenance も同様
  - 依存関係による同時更新: タイトルは 1 パッケージでも、バージョンを完全一致で固定し合うパッケージ群（例: Rails の activestorage と actionpack などの gem）は lockfile 上で一緒に上がる。タイトルだけで判断せず、diff で実際に上がったパッケージを確認する
- 先にパッケージ名・新旧バージョンを取り出しておくと、以降の調査やセクションの当たりを付けるのが早い

## 情報収集

情報源の優先順位（上から順に確実性が高い）:

1. PR の diff と manifest / lockfile の変更内容（実際に何が変わるかの一次情報）
2. PR body に bot が埋め込む各種セクション
3. Release Notes / CHANGELOG（body にリンクがあれば確認）

ただしセキュリティ面（CVE/GHSA・深刻度・影響範囲・修正導入版）に限れば、紐づく Dependabot alert（後述）が最も確実な一次情報で、Release notes より優先する。

ghro コマンド例:

- メタ情報: `ghro pr view <PR番号> --repo owner/repo --json number,title,author,body,headRefName,labels,additions,deletions,files`
- 差分本体: `ghro pr diff <PR番号> --repo owner/repo`
- CI 状況: `gh pr checks <PR番号> --repo owner/repo`
- Dependabot alert 一覧: `ghro api 'repos/<owner>/<repo>/dependabot/alerts?state=open&per_page=100' --paginate --jq '.[] | {number, package: .dependency.package.name, manifest: .dependency.manifest_path, ghsa: .security_advisory.ghsa_id, cve: .security_advisory.cve_id, severity: .security_advisory.severity, range: .security_vulnerability.vulnerable_version_range, first_patched: .security_vulnerability.first_patched_version.identifier}'`（デフォルトは全 state・1 ページ 30 件で取りこぼすので、open に絞ってページングする。open な alert が 0 件なら何も出力されない。取得失敗とは終了コードで見分ける）

不明な点は推測せず「未確認」と記載する。

### Dependabot body の読み方

Dependabot は body に決まったセクションを埋め込むので、該当箇所だけ拾う:

- `Release notes` — 各バージョンのリリースノート。Breaking Changes / セキュリティ修正の主な情報源
- `Commits` — 期間内のコミット一覧。リリースノートに載らない小さな破壊的変更が出ることがある

### Renovate body の読み方

- 冒頭の表 — 更新対象のパッケージ・種類・更新種別・旧→新バージョン
- `Release Notes` — パッケージごとに折りたたまれたリリースノート。中間バージョンも含めて全部読む。Commits セクションはないので、必要なら各バージョンの "Compare Source" リンクか後述の compare API で補う
- `GitHub Vulnerability Alerts` — セキュリティ修正の PR にだけ付く。タイトル末尾が `[SECURITY]` になることが多い。ただしこれは手がかりで、判定は Dependabot alert 一覧で行う
- `Configuration` — schedule や automerge の設定。レビュー判断にはほぼ使わない

Renovate 固有の CI チェック:

- `renovate/stability-days` は `minimumReleaseAge` を満たしたかを示す。pending の場合はリリース直後なので、その旨を CI 状況に書く

### GitHub Actions の SHA pin

`uses: owner/repo@<SHA> # vX.Y.Z` 形式で pin されている場合、SHA が本当にそのタグの commit かを確かめる。コメントのバージョンだけ書き換えて別の SHA を指す改ざんを見抜くため:

- `ghro api repos/<owner>/<repo>/commits/<タグ> --jq .sha` でタグの commit SHA を取る（annotated tag でも commit まで解決される）
- 新旧どちらの SHA も確認し、同じ action の sub action（`init` / `analyze` など）が同じ SHA に揃っているかも見る

### 上流 release 差分（補助情報）

レジストリ tarball と git タグの中身は一致しないことがあるため、これだけで混入の有無は言い切れない。あくまで「不審な変更の手がかり」を得るための補助。PR body のリンク（Dependabot の "Updates ..."、Renovate の "Compare Source"）やパッケージメタ情報から上流リポジトリを特定し、compare を確認する:

- URL 例: `https://github.com/<owner>/<repo>/compare/<旧タグ>...<新タグ>`
- ghro 経由: `ghro api repos/<owner>/<repo>/compare/<旧タグ>...<新タグ>`（commits / files / 差分行数を JSON で取得。commits は 250 件、files は 300 件で打ち切られるので、上限に達したらその旨を「未確認事項」に書く）

着目点:

- `postinstall` / `preinstall` / `bin` / `scripts` フィールドの追加・変更
- GitHub Actions なら `action.yml` の `runs`（`using` / `main` / `post`）や inputs の追加・変更
- 不審な URL / IP / Base64 / 長文字列の追加
- 変更内容に対して不自然に大きい diff（minify ファイルの差し替えなど）
- 既知メンテナでない author によるコミット

git diff では検出できないものがあるので過信しないこと:

- レジストリ tarball にのみ混ぜられた悪意コード（git タグと publish 内容が一致しない場合）
- 難読化 / 時限発火 / 環境依存で動作するコード
- 間接依存（依存先の依存）への混入
- 乗っ取られたメンテナアカウントから push されたタグ（署名検証なしでは正当性を保証できない）

### Dependabot alert 起因かを必ず確認する

依存更新 PR にはバージョンアップ起因とセキュリティ修正起因があり、後者だけがリポジトリの Dependabot alert に紐づく。Renovate もリポジトリの Dependabot alert を読んでセキュリティ修正 PR を作るので、bot の種類に関わらず確認方法は同じ。PR 単体ではどちらか判別しづらく、PR と alert の紐づけは API でも直接は取れないため、alert 一覧と比べて判定する。セキュリティ起因かどうかに関わらず毎回実施する:

- 上の「Dependabot alert 一覧」コマンドで alert を取得し、PR と次がすべて一致する alert を探す
  - パッケージ名が一致
  - manifest パスが一致（例: `package-lock.json`）
  - `range` に現行バージョンが含まれ、`first_patched` を PR の新バージョンが満たす（＝この PR で解消される）
  - state が open であること（未解消）は一覧コマンドの `state=open` で保証済み
- 一致する alert があれば、その PR は alert 起因（セキュリティ修正）。見つからなければ通常のバージョンアップ起因と判断する

一致した alert の詳細を引けば、Release notes に載らないこともある CVE/GHSA・深刻度・影響範囲・修正導入版を確実に取得でき、これがセキュリティ判定の一次情報になる:

- `ghro api repos/<owner>/<repo>/dependabot/alerts/<番号> --jq '{number, state, ghsa: .security_advisory.ghsa_id, cve: .security_advisory.cve_id, severity: .security_advisory.severity, summary: .security_advisory.summary, range: .security_vulnerability.vulnerable_version_range, first_patched: .security_vulnerability.first_patched_version.identifier, url: .html_url}'`
- ユーザーから alert の URL/番号を直接渡された場合は、その番号で詳細を引くのが最短

1 つの PR が複数の脆弱性を一度にまとめて修正することもあるので、複数の alert が一致しないか意識する。複数パッケージを更新する PR では、パッケージごとに確認する。

## 出力形式

各項目は diff・PR body・Release notes・Dependabot alert を調べ、判断と根拠をあわせて記載する。テンプレートの各フィールドがそのまま調査すべき観点になる。上流 release 差分（補助）で不審点があれば「未確認事項」または「結論」で触れる。

複数パッケージを更新する PR では、概要のパッケージ行をパッケージごとに並べ（依存関係で一緒に上がるパッケージ群は 1 行にまとめてよい）、主要な確認結果もパッケージごとの差異が分かるように書く。

`tmp/docs/pr-review-{PR番号}.md` に以下の構成で出力する:

```markdown
# PR {PR番号}: {PRタイトル}

## 概要

- パッケージ: {パッケージ名} {旧バージョン} → {新バージョン}
- 依存の種類: {ランタイム依存 / 開発依存 / GitHub Actions など}
- バージョン変更: {メジャー / マイナー / パッチ / digest}

## 主要な確認結果

- Breaking Changes: {有無と詳細}
- セキュリティ: {紐づく Dependabot alert と CVE / GHSA・深刻度・影響範囲・修正導入版。この PR で解消されるか。なければ「なし」}
- サポートバージョン: {言語・ランタイムの最低バージョン変更の有無}
- CI 状況: {pass / fail / pending と失敗の概要}
- 連鎖更新: {更新対象以外の依存変更の有無。依存関係で一緒に上がるのが当然のものか、意図しない変更かを分けて書く}

## 影響範囲

{manifest / lockfile / diff から見えるアプリケーションコードへの影響。GitHub Actions の場合は、その action を使う workflow と（reusable workflow なら）呼び出し元への影響、SHA pin の確認結果を書く}

## 未確認事項

{情報不足や追加確認が必要な点。なければこのセクション自体削除すること}

## 結論

{問題なし / 要確認 / マージ非推奨}

{判断の根拠を簡潔に}
```

## 注意事項

- このスキルはレビューと報告のみを行い、PR のマージや承認は行わない
- 出力するレポートは PR レビューコメントとして GitHub に投稿する前提で書く。GitHub-flavored Markdown の自動リンクに注意する:
  - 裸の `#123` は Issue/PR へ自動リンクされてしまうので、そのまま書かない（見出しも `PR 123` とする）
  - Dependabot alert 番号は `[alert #123](https://github.com/<owner>/<repo>/security/dependabot/123)` のように対象 URL への Markdown リンクにする。セキュリティ欄・結論など、言及するたびに毎回リンクにする
